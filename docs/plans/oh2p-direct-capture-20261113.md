# OH2P 直接文本记录核查（未采用）

2026-11-13 用户明确要求完整聊天，拒绝用设备可见文本替代。本文件的设备事件采集设计仅作核查记录，不进入实施。后续用户确认采用角色介绍约束小智主动调用 MCP 逐轮写入，并明确授权继续修改代码，不以模型行为实测作为实施前置。当前实现该主动记录路线，NAS 部署仍留待以后。UI 由用户指定 Astra（high）处理。

## 目标与限制

长期运行不依赖网页登录凭据；正式部署到家庭 NAS Docker，本轮只做本地代码与验证，不改家庭实例。

现有 OH2P 链路能被动接收 STT 识别文本与 TTS 分句拟播文本，可以保存设备可见的文本事件。不能据此声称取得云端完整消息历史、全部工具调用结果或准确的已播放文本。后台未发送的内容、被采集前的断线丢失，无法补录。

## 源码依据

- 固定上游版本由公开仓 `server/Dockerfile` 和 `server/prepare_source.py` 指定，提交为 `bc3396c`。
- WebSocket 入站 JSON 在协议层进入 `on_incoming_json`，之后应用分发 STT/TTS/情绪；音频走二进制数据。
- 现有连接级会话标识不等于逐轮回复标识；TTS stop 不等于音箱播放完成，打断会清理尚未播放的数据。
- 采集必须在应用有界队列之前，不能依赖可能丢弃的下行显示队列。

## 曾评估的设备采集路径（已否决，不实施）

1. OH2P 接入服务在收到文本事件时生成稳定事件 ID、采集实例 ID、连接会话 ID 和单调序号，保存受控字段，不记录音频、认证头或握手凭据。
2. 先写持久化待投递队列，再异步批量投递到 NAS 内部的记忆服务；失败保留、重试沿用事件 ID，接收端幂等落库，确认成功后清理待投递数据。
3. 记忆服务保留原事件，将 STT 和 TTS 文本分别投影为用户识别文本和助手拟播文本；打断、重连及采集缺口保留。角色不推断家庭成员身份，不拼造缺失回复或工具结果。
4. 摄取通道独立于 MCP，使用专用本地认证和固定智能体绑定；模型仅通过 MCP 读取来源、检索与提炼，不能伪造采集原文。
5. 本地合成事件验证重启恢复、乱序/重复拒绝或幂等、断线重试、长度限制、身份隔离及不泄露凭据。实际设备事件覆盖、音频延迟与 NAS 容器持久化以后再验收。

## 已确认的产品边界

用户要求“云端逐句完整原文及工具消息”，当前协议证据不足，不能通过降低标准把方案标为可行，需要继续找有完整事件能力的接入层。用户再次澄清“继续用 MCP 调取”仍指完整云端聊天，并明确要求先不修改采集逻辑；不是授权模型自行补写聊天，也不是只读取现有本地档案。

## 云端完整来源的进一步核查

截至本轮检索，没有找到能确认向普通账号开放、无需网页登录凭据且覆盖完整正文与工具消息的官方长期接口。此结论是证据不足，不是断言不存在。

| 路线 | 一手证据 | 判断 |
| --- | --- | --- |
| 设备 WebSocket | [官方协议](https://github.com/78/xiaozhi-esp32/blob/main/docs/websocket.md#42-server---device)描述识别文本、TTS 分句、表情和设备 MCP；[当前固定客户端](https://github.com/idootop/open-xiaoai/blob/bc3396c64e2a435f354eb5cb12a203981f1fe422/examples/xiaozhi/xiaozhi/xiaozhi.py#L213-L278)只分发相关设备事件 | 不满足云端完整原文要求，已否决 |
| MCP | 官方工具发现/调用协议不等于云端历史订阅；当前客户端没有完整聊天读取工具 | 不能用工具调用补写代替原文 |
| 官方历史导出/API | [官方仓议题](https://github.com/78/xiaozhi-esp32/issues/2198)有人请求导出和正式 API；用户议题不等于官方承诺 | 未确认支持范围或开放时间 |
| 开发者密钥 | [M5Stack 实现](https://github.com/m5stack/StackChan/blob/main/server/internal/xiaozhi/xiaozhi.go#L542-L562)用配置中的 `secret_key` 调用 `/api/developers/token`；[请求封装](https://github.com/m5stack/StackChan/blob/main/server/internal/xiaozhi/xiaozhi.go#L73-L120)使用 Bearer 且过期后重新兑换 | 存在候选认证路线，但不等于当前账号可申请或能读取完整历史 |

M5Stack [会话列表代码](https://github.com/m5stack/StackChan/blob/main/server/internal/xiaozhi/xiaozhi.go#L709-L732)用于删除流程，未展示消息正文分页及工具结果读取。本轮只读源码，未执行删除接口。[配置说明](https://github.com/m5stack/StackChan/blob/main/server/README.MD#58-xiaozhi)仅给出密钥占位，没有普通账号申请入口。客户端定时刷新策略不能作为官方 token 有效期保证。

进入采集实现前需要确认：开发者密钥取得途径、普通账号资格、是否覆盖现有智能体、完整正文及工具消息读取接口、分页与保留语义、长期认证续期机制。当前没有这些条件，不编造接口、不将网页 token 换名当长期密钥、不替用户发送申请邮件。

## 新候选：模型主动通过 MCP 逐轮记录

用户进一步说明其方案：利用小智优先调用 MCP 的能力，每轮对话主动调用本项目的记录工具，由本地脚本保存会话。此前仅评估云端历史拉取不充分；此主动推送路径单独评估，不因没有历史查询接口直接否决。

工具可接收模型提交的文本并写库，无需网页历史凭据。[官方 MCP 协议](https://github.com/78/xiaozhi-esp32/blob/main/docs/mcp-protocol_zh.md#6-工具调用)有带参数的工具调用机制，但该机制本身没有证明会自动附带完整聊天上下文，或每轮最终回复后必定触发一次调用。现有 `src/memory/mcp.ts` 的 `memory_capture_candidate` 只接收最多 2000 字文本和原因，是暂存候选，不能直接改名当完整聊天日志。

已授权实施方案：专用逐轮追加工具接收角色与正文，服务端生成记录标识、落库回执并处理重试；模型角色提示要求逐字提交、不得摘要或补写，缺失显式标记。工具结果由模型按可见内容提交；本轮不另加全局工具拦截器。记录本身不递归作为下一次待记录工具事件。

用户明确取消模型行为实测前置；本轮验证代码的落库、幂等、身份隔离、读取与来源标注，不连接真实模型做覆盖率试验。产品将这些数据标为模型提交，助手区分拟回复、最终回复或未注明；不声称平台保证零遗漏，也不声称补齐模型看不到的过去历史。先前“暂不改采集逻辑”的暂停由本次明确实施授权解除。
